Fragmented Keys

Tag-versioned composite cache keys — invalidation without bulk deletes.

What it is How keys are built Why it matters Implementations Quickstart Status GitHub

What it is

Fragmented Keys is an open-source cache-invalidation library. A cache key is composed from a key name, a group id, and an ordered set of independently versioned “tags”; the composite key is the MD5 of that string. When any tag’s version is bumped, the composite hash changes, so every dependent cache entry becomes unreachable instantly — with no bulk deletes and no tombstones. Stale entries simply age out under their normal TTL.

How keys are built

The shared, language-agnostic construction rule from the spec:

Key = MD5("KeyName_GroupID:tTag1:vVer1:tTag2:vVer2...")
  • KeyName — the human-readable key name (e.g. Dashboard).
  • _ separates the key name from the group id; : separates every subsequent field.
  • Each tag contributes t<TagName> then v<Version>, in the order the tags were supplied — field order is significant.
  • Every tag carries an independently stored version counter; a fresh version is seeded from microtime on reset. Constant tags hold a fixed version and model dimensions that never change (site, environment).

Worked example

A concrete rendering, taken from the Go implementation’s test vectors (global prefix GNP, tag User instance 42 at version 1748000000000.0, tag City instance chicago at version 5.0):

Key("Dashboard", [User:42, City:chicago])
  -> md5("Dashboard_:tUser_42GNP:v1748000000000.0:tCity_chicagoGNP:v5.0")
  =  371011c8520b2129c3231b1396adab4d

user.Increment(ctx)          # one write: version 1748000000000.0 -> 1748000000000.1

  -> md5("Dashboard_:tUser_42GNP:v1748000000000.1:tCity_chicagoGNP:v5.0")
  =  a different key          # guaranteed miss; the old entry is never deleted

The entry built from the old hash is not deleted — it becomes unreachable and expires under its own TTL. Note the global prefix appended to each tag name (User_42GNP): the Python, Django and Go ports support an app-level prefix so several applications can share one cache namespace.

Why it matters

Classical cache invalidation makes you choose: delete entries one by one (and track down every key you ever wrote), flush a whole namespace (and eat the resulting database spike), or maintain tombstones. Fragmented Keys replaces all three with one integer write:

  • No bulk deletes, no tombstones. Bumping a tag’s version changes the composite hash, so every dependent entry resolves to a new key instantly; stale entries expire naturally under TTL.
  • Tree-structured invalidation granularity. Invalidate everything tied to User:42, or everything tied to Global.Greeting, with the same single call — you choose the blast radius when you design your tags.
  • Backend-agnostic. All storage sits behind a cache-handler abstraction with get, set and a bulk get_multi; reference handlers cover in-memory (dev/test) and Redis (bulk ops via MGET/MSET).
  • Bulk-fetch optimization. Tags are grouped by handler so all version lookups needed to build one composite key resolve in a single round trip.
  • KeyRing templates. Named key definitions binding an ordered tag list to handler configuration give you a factory/reuse layer on top of raw key construction.

Implementations

One spec, eight languages. Each implementation lives in its own upstream repo and appears as a directory in the composite repository (assembled with git subtree, so every variant keeps its own history behind its prefix).

Not every port produces byte-identical keys today: per the Go implementation’s compatibility notes, the PHP, Python, Elixir and TypeScript ports (and Go itself) agree on MD5, the :t/:v separators, the _ name separator, float versions with a +0.1 increment, and insertion-ordered tags — while the Java and Swift ports sort tags rather than preserving insertion order (and Swift skips hashing entirely). That divergence predates the Go port.

Quickstart

Elixir

# mix.exs
def deps do
  [
    {:fragmented_keys, "~> 0.1.0"}   # add :redix ("~> 1.5") for the Redis handler
  ]
end
handler = FragmentedKeys.CacheHandler.Memory.new()
FragmentedKeys.Configuration.set_default_cache_handler(handler)

tag_user = FragmentedKeys.Tag.Standard.new("User", "42")
tag_city = FragmentedKeys.Tag.Standard.new("City", "chicago")

key = FragmentedKeys.Key.new("Dashboard", [tag_user, tag_city])
key_str = FragmentedKeys.Key.get_key_str(key)   # => MD5 hex digest

# Invalidate every key depending on User:42 — one write, no deletes
FragmentedKeys.Tag.increment(tag_user)

Python

pip install fragmented-keys   # or: uv add fragmented-keys
from redis import Redis
from fragmented_keys import Configuration, RedisHandler, StandardTag, StandardKey

client = Redis(host="127.0.0.1", port=6379)
Configuration.set_default_cache_handler(RedisHandler(client))

user_tag = StandardTag("User", "42")
city_tag = StandardTag("City", "chicago")

key = StandardKey("UserDashboard", [user_tag, city_tag])
cache_key = key.get_key_str()          # MD5 hex digest

data = client.get(cache_key)
if data is None:
    data = fetch_from_database()
    client.set(cache_key, data)

# Invalidate all keys depending on User:42
user_tag.increment()

Go

go get github.com/noizu-labs/fragmented-keys-go
import (
    "github.com/noizu-labs/fragmented-keys-go/djangoredis"
    "github.com/noizu-labs/fragmented-keys-go/fragkeys"
    "github.com/redis/go-redis/v9"
)

rdb := redis.NewClient(&redis.Options{Addr: "…:6379", DB: 1})
h := djangoredis.New(rdb, djangoredis.WithCompression(true))
fragkeys.Config.SetDefaultCacheHandler(h)

tag := fragkeys.NewStandardTag("Page", "careers")
doc, found, err := h.GetWithTags(ctx, "content_page", []fragkeys.Tag{tag})
if err != nil || !found {
    doc = compute()
    _ = h.SetWithTags(ctx, "content_page", doc, []fragkeys.Tag{tag}, 10*time.Minute)
}

// Invalidate for both runtimes at once (shares a cache with Django).
_ = h.InvalidateTags(ctx, []fragkeys.Tag{tag})

Status

Honest conformance status. Cross-language test vectors are not yet promoted into the spec: each implementation is tested only in its own language’s harness, and no shared fixture set asserts that all eight ports produce identical composite keys for identical inputs. The Go port does verify against golden keys generated by running the Python port (raw string and MD5), but spec/ does not yet pin the MD5 hex casing or the exact rendering of version integers inside the pre-hash string — so implementations could diverge silently while each remaining self-consistent. Do not treat cross-language key equality as guaranteed until a shared vector set lands in the spec.
